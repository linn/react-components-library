# Signed-in requests (useGet, usePut, usePost, useDelete)

What `useGet`, `usePut`, `usePost` and `useDelete` share. Each keeps its own signature and state (see its page); with `requiresAuth` they make the request as the signed-in user, from react-oidc-context's `AuthProvider` or, in an app on redux-oidc, a [`RequestAuthProvider`](?path=/docs/hooks-requestauthprovider--docs).

## Waiting for the token

Each hook returns `hasToken`: `true` once the user has a token that hasn't expired. Once it's true it stays true while that token expires and is renewed (so a page loading on `hasToken` doesn't load again and lose the user's edits); it's `false` again only when there's no token. A page whose endpoint needs sign-in waits for it rather than sending too early:

```jsx
const { send, hasToken, result } = useGet(itemTypes.plans.url, true);

useEffect(() => {
    if (hasToken) {
        send(code);
    }
}, [hasToken, code, send]);
```

`send` itself never waits: called with no token yet, the request goes without one (as not signed in). This relies on the app signing the user in when there's no user or theirs has expired: react-oidc-context's `useSignIn` does this (an expired user isn't `isAuthenticated`), and so does an app on redux-oidc that signs in before rendering. A stored token that has already expired isn't renewed silently by oidc-client-ts, so in an app that does neither, a page waiting on `hasToken` would wait for ever. (`useInitialise` with `requiresAuth` waits the same way, by itself.)

`send` keeps its identity when the token is renewed in the background, so a page that loads in an effect on `send` doesn't load again and lose the user's edits. It does change when `hasToken` does, so a page that sends in an effect on `send` without checking `hasToken` loads again once there's a token, as these hooks always have.

## What send returns

`send` returns a promise of the outcome, as well as setting the hook's state:

**Showing an error safely:** `errorMessage` can be a stack trace or an HTML error page. To show the user only what the API meant them to see, use `apiMessage` with a sentence of your own:

```jsx
const outcome = await send(code, changes);
if (!outcome.superseded && !outcome.ok) {
    setProblem(outcome.apiMessage ?? "Your changes couldn't be saved. Please try again.");
}
```

## Without a URL of its own

Give the hook no `url` (`null`) and `send`'s first argument is the whole URL: for a page that follows the links in a resource.

```jsx
const { send: putPlan } = usePut(null, true);
await putPlan(`${config.appRoot}${utilities.getHref(plan, 'edit')}`, changes);
```

## A rejected token: signing in again

When the API rejects the token a request carried (expired, say), the outcome and the hook's state have `tokenRejected: true`. **The hooks don't sign in again by themselves:** that would send the browser off to sign in, and a page with unsaved edits would lose them without warning. The page decides, with `signInAgain()`, which each hook returns:

```jsx
const outcome = await putPlan(code, changes);
if (outcome.tokenRejected) {
    // a page with unsaved edits can say so first, or rely on a leave-page prompt
    signInAgain();
}
```

`signInAgain` signs in with the app's own sign-in, at most once a minute, so a page calling it whenever a token is rejected can't loop on a token that keeps being refused. A page with nothing to lose (a report, say) can call it straight away. A page with edits should also tell the user their sign-in has expired, with a button for `signInAgain({ force: true })`: the user may have stayed put (on a leave-page prompt, say) to keep their edits, and their own click skips the once-a-minute limit.

`tokenRejected` goes by the API's **bearer challenge**, a `401` with `WWW-Authenticate: Bearer error="invalid_token"`, not by the body: any other `401` is the app's own refusal (often "you don't have permission", or "Could not identify the logged in employee"), which signing in again won't fix. A request sent before there was a token isn't `tokenRejected` either, even if the API challenges it: the app's own sign-in (`useSignIn`) deals with a user who isn't signed in yet.

Only an API that sends the bearer challenge can report a rejected token:

- **`app.UseBearerTokenAuthentication()`** from `Linn.Common.Authentication.Host` 5.0.0 or later, after `app.UseAuthentication()`. Referencing the package isn't enough: an API on plain `UseAuthentication()` treats a rejected token as no sign-in at all, and answers as it would anyone not signed in.
- **For local development**, where the dev server calls the API on another port, the API's CORS settings must expose the header, or the browser hides it from the page: `builder.AllowAnyOrigin().AllowAnyMethod().AllowAnyHeader().WithExposedHeaders("WWW-Authenticate")`.

Without them a rejected token is just a failed request, like any other refusal.

With react-oidc-context, `signInAgain` sets `sessionStorage['auth:redirect']` to the current path and query string, as `useSignIn` does, so the app's `onSigninCallback` brings the user back. With a `RequestAuthProvider`, the app's own `signIn` decides how to come back.
