# useSignedInRequest (useSignedInGet, useSignedInPut, useSignedInPost)

Requests as the signed-in user (from react-oidc-context's `AuthProvider`, or a [`RequestAuthProvider`](?path=/docs/hooks-requestauthprovider--docs) for an app on redux-oidc), for pages that need more than `useGet`, `usePut` and `usePost` give. Unlike those, it:

- reports `hasToken`, so a page can wait for the sign-in token rather than send an empty one;
- marks an answer `superseded` when a newer request (or `clearData`) has happened since, and doesn't keep it;
- turns a network failure into a failed outcome, never a thrown error or endless loading;
- signs in again when the API rejects the token, at most once a minute so a token that keeps being refused can't loop. It goes by the API's bearer challenge, a `401` with `WWW-Authenticate: Bearer error="invalid_token"`, not by the body: any other `401` is the app's own refusal (often "you don't have permission", or "Could not identify the logged in employee"), which signing in again won't fix, so its message is shown instead;
- never hands the server's raw body to the page: `errorMessage` is only a 4xx's JSON-string message, how `Linn.Common.Service` writes a `BadRequestResult`. A stack trace or HTML error page gives `null`, and the page says something of its own;
- keeps `send`'s identity when the token is renewed in the background, so a page that loads in an effect on `send` doesn't load again and lose the user's edits.

## Signature

```js
const { send, isLoading, ok, result, status, errorMessage, clearData, hasToken } = useSignedInGet();
// also useSignedInPut(), useSignedInPost(), or useSignedInRequest('DELETE') for any method
```

`send(url, body?)` takes the whole URL (the hook has none of its own) and an optional body, sent as JSON. It returns a promise of the outcome:

The latest outcome (without `superseded`) is also kept as state: `isLoading`, `ok`, `result`, `status`, `errorMessage`. `clearData()` empties it and drops any answer still on its way. `hasToken` is `true` once the user has a token that hasn't expired. It relies on the app signing the user in when there's no user or theirs has expired: react-oidc-context's `useSignIn` does this (an expired user isn't `isAuthenticated`), and so does an app on redux-oidc that signs in before rendering. A stored token that has already expired isn't renewed silently by oidc-client-ts, so in an app that does neither, the page would wait (loading) for ever.

## Usage

```jsx
import { useSignedInGet, useSignedInPut } from '@linn-it/linn-form-components-library';

function Plan({ code }) {
    const { send: getPlan, hasToken, result: plan } = useSignedInGet();
    const { send: putPlan } = useSignedInPut();
    const [problem, setProblem] = useState(null);

    useEffect(() => {
        if (hasToken) {
            getPlan(`/plans/${encodeURIComponent(code)}`);
        }
    }, [hasToken, code, getPlan]);

    const save = async changes => {
        const outcome = await putPlan(`/plans/${encodeURIComponent(code)}`, changes);
        if (outcome.superseded) return;
        if (!outcome.ok) {
            setProblem(outcome.errorMessage ?? "Your changes couldn't be saved. Please try again.");
        }
    };
    // ...
}
```

## What the API needs for signing in again

Only an API that sends the bearer challenge gets a user signed in again:

- **`app.UseBearerTokenAuthentication()`** from `Linn.Common.Authentication.Host` 5.0.0 or later, after `app.UseAuthentication()`. Referencing the package isn't enough: an API on plain `UseAuthentication()` treats a rejected token as no sign-in at all, and answers as it would anyone not signed in.
- **For local development**, where the dev server calls the API on another port, the API's CORS settings must expose the header, or the browser hides it from the page: `builder.AllowAnyOrigin().AllowAnyMethod().AllowAnyHeader().WithExposedHeaders("WWW-Authenticate")`.

Without them a rejected token just fails like any other refusal: nothing loops and nobody is bounced to sign in, but nobody is signed in again either.

With react-oidc-context, signing in again sets `sessionStorage['auth:redirect']` to the current path and query string, as `useSignIn` does, so the app's `onSigninCallback` brings the user back. With a `RequestAuthProvider`, the app's own `signIn` decides how to come back.
